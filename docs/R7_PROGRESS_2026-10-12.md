# R7 protected catalog activation — source preparation

Scope is the confirmed draft in `R6_DESIGN_20261011.md`: the SYSTEM Warden
reads protected catalog authority, probes using a free shared slot, then atomically
publishes a generation without rewriting historical job captures. There is no
loopback activation endpoint: the owner token is readable by agents. Optional
batch/canary/sentinel proposals are not added to this scope.

Implemented the pure change-plan compiler in `catalog_activation.py`:

- Binds exact proposal bytes and the expected current policy digest.
- Rejects duplicate/unknown fields, legacy policy migration and reused generations.
- Keeps operational budgets, backoffs, pools and matching model caps intact;
  refuses to silently discard an explicit cap on a retired target.
- Captures immutable candidate bytes, deduplicated changed targets and an existing
  control target. Mutating the input/projection cannot alter its digest.
- Requires new generation identity even for reorder-only changes, with a control
  probe planned. A plan explicitly grants no activation authority or acceptance.

## Retained protected authority reader

`catalog_authority.py` now prepares the SYSTEM-only reader. Its production entry
point accepts no pathname and reads the fixed Program Files catalog authority
root. It retains ancestors top-down against rename/deletion and holds the pointer
and proposal files against writing or replacement through the caller's context.
ACL validation follows acquisition, reparse objects/hardlinks are rejected, and
the proposal leaf is derived exclusively from its pinned SHA256. Strict bounded
pointer parsing rejects duplicate keys, extra paths, invalid IDs and oversized
files. Failure or caller exceptions release handles in reverse order.

The Windows adapter is tested with injected API/metadata fixtures; these are not
native share-mode or SYSTEM ACL acceptance. No protected directory was created or
read by these tests. This reader does not publish a generation, reserve a slot or
grant loopback authority. Remaining integration listed above is still required.

## Transactional publication primitives

`catalog_journal.py` adds explicit transaction-bound journal initialization and
generation publication, currently **not installed or invoked by JobStore**.
It requires FULL synchronous writes and foreign keys, preserves immutable
generation history, checks the expected prior policy, and publishes through an
atomic singleton pointer update. A replay returns the old request's receipt
without moving the active pointer backward. Initialization refuses an unrelated
installed baseline. Probe projections must exactly cover changed targets plus
the control and bind request, plan, cleanup and reservation identities.

These checks do not prove that a supplied reservation was live: the upcoming
JobStore integration must verify and consume real shared-slot reservations in
that same transaction. No controller/API path can call publication yet. Tests
cover transaction rollback, concurrent-reader visibility, reopened-file recovery,
replay/stale proposals, missing cleanup and unbound proofs, using temporary SQLite

## Durable shared-capacity and fenced probe evidence

`catalog_slots.py` now provides explicit-migration probe accounting on the job
board. Reservations bind the protected request/plan/file digests, target, worker,
containment nonce, boot identity and monotonic fencing token. Ordinary job claims
count unfinished probes against the same capacity and refuse an occupied worker;
probe reservations count existing jobs, active worker routes and cleanup barriers.
The probe allocator permits at most the owner's four shared slots.

Expiry does not release capacity or authorize a new probe. Restart preserves
occupancy, and a repeated request/target is refused. Only the trusted integration's
fenced cleanup confirmation releases the slot; a late or failed probe remains
ineligible for publication. Immutable identity/history/outcome triggers preserve
evidence. The publication wrapper uses recorded results, checks exact authority
bindings and consumes them in the same transaction as generation publication.
Rollback leaves both the active generation and evidence consumption unchanged.

This is capacity/evidence plumbing, not a dispatch API: provider/pool/model-cap
admission, the native executor and its trusted cleanup attestations still need
integration before probes may run. Runtime/config integration, protected migration
and the reviewed R7 owner package remain outstanding. No controller endpoint was
added, and no installed database or delivered R6 package was modified.

## Completed runtime integration and owner sitting

R7 source now integrates the protected-pointer reader, journal and probe ledger
into Runtime behind the explicit `catalog_activation` flag. Enabling it requires
v3 routing, four shared slots and an already migrated database. It exposes only
sanitized read-only status, with no loopback activation endpoint. New submissions
and dispatch accounting use the active generation transactionally; the operator
view now reads that same durable authority instead of the installed baseline.

Catalog probes occupy the shared native/Docker budget and the same model,
provider and quota-pool limits as normal jobs. Existing holds block probes.
Warm Docker seats must drain before a probe reserves a seat. Production probes
use NativeRunner with exact selectors, inference restrictions, RAM validation,
fenced leases and verified cleanup. Full native logs remain private; a durable
sidecar binds their receipt/output hashes to the protected proposal and actual
capacity fence. A scheduled-task Warden owns a separate catalog fencing nonce,
without depending on an optional supervisor launch environment variable.

Successful results are consumed in the same transaction that publishes the
generation. Restart preserves unresolved occupancy, never guesses cleanup and
never automatically repeats a failed request. Completed probes can be consumed
after restart without another model call. A changed protected pointer can be
processed by the same running coordinator; replay never moves authority backward.

`r7_migration.py` performs an explicit owner-run SYSTEM migration while holding
the service lock. It refuses a busy board, unresolved cleanup, live routes or
existing catalog schema. A full SQLite backup is kept and every original table
and row is checked before/after migration. Snapshot hashing streams rows rather
than retaining the whole database in Python memory. Before any R7 start, rollback
may restore this backup only if the original records still match. Uncertain
migration or any requested R7 start holds state for review rather than resetting
the board. Backup, tasks and partial roots are never deleted.

The new `run_r7_launch.ps1` owner entry point includes pending R6 recovery as a
prerequisite. It reuses an already completed R6 deployment. Otherwise it invokes
a fresh copy of the reviewed `eb982cb` recovery with one change: its input deadline

The owner sitting requests temporary system wakefulness on its own thread and
